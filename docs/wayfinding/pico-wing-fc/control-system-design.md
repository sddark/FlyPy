# Control system design

Type: grilling (HITL)

## Status

resolved 2026-07-29

## Question

Define the control core of the spec: loop rate(s), PID structure for pitch/roll (and yaw handling for a V-tail), rate-vs-attitude loop nesting per flight mode, the V-tail mixer (elevator/aileron → left/right surface equations, throws, directions), throttle path (manual vs stabilized vs autonomous), channel mapping from CRSF, and the full list of tunable parameters with ranges and defaults — everything the web config must expose. Blocked by "Research: MPU6050 attitude estimation" (estimator choice shapes the loops) and "Research: MicroPython platform feasibility" (achievable rates).

## Assumptions

- **Transpile from INAV** (surveyed, see "Research: INAV transpile survey"): fixed-wing PID from `flight/pid.c` (~1510 lines, port fixed-wing path only), V-tail mixer from `flight/mixer.c` (~739 lines, V-tail table row only), attitude estimator from `flight/imu.c` (~986 lines, Mahony-family — matches the MPU6050 research part). This part becomes "adapt INAV's fixed-wing controller" not "design a controller".
- **Bespoke:** MicroPython MPU6050 driver and servo/ESC PWM/Oneshot125 output have no INAV counterpart.
- Modes are manual / stabilized / autonomous (autonomous feeds its own demands into these loops).
- V-tail only; no rudder channel, no coordinated-turn logic.
- All loop parameters are web-configurable, per owner.

## Decision

- **Loop rate:** single 250 Hz flight loop (all axes, mixer, and outputs run together — no separate outer/inner loop rates for the MVP).
- **Manual mode:** raw stick passthrough — pitch/yaw channels feed the mixer directly, no PID. Throttle passthrough. Roll stick is unused in this mode.
- **No roll axis / actuator:** the airframe has 2 V-tail servos and no ailerons — there is no physical roll actuator. **Roll stick drives turn coordination, not a roll PID.**
- **Stabilized mode — full INAV-cascade, not a bespoke simplification (revised 2026-07-29):** the first implementation used a single loop directly on angle error for pitch, and no feedforward anywhere. Bench math showed this saturates the output at every meaningful stick input (a 1° pitch error or a 10% yaw stick both hit the output clamp instantly) — the human-friendly gain values (4.0, 2.0, ...) were being multiplied directly against real degree/deg-per-second errors with no scale factor, unlike INAV's own pipeline. Fixed by adopting INAV's real architecture and constants wholesale:
    - **Pitch — outer level loop → inner rate loop.** `pidLevel()` (`flight/pid.c` line 689-726): `angleRateTarget = clamp(angleErrorDeg * (levelP * FP_PID_LEVEL_P_MULTIPLIER), ±rateLimit)`, `FP_PID_LEVEL_P_MULTIPLIER = 1/6.56` (`flight/pid.h` line 47). `pitch_level_p` (INAV `fw_p_level`, default 20) is the level gain; `pitch_rate_limit_dps` (INAV: configured acro rate × 10, default 200 dps, matching `pitch_rate` default 20 decidegrees/s) is the ceiling. INAV never gives yaw an angle mode (`pid.c` line 1280: the level-loop axis range is `FD_ROLL` to `FD_PITCH` only) — confirms yaw stays rate-only.
    - **Inner rate loop, both pitch and yaw — P+I+D+FF, INAV's real constants.** `pidApplyFixedWingRateController()` (`flight/pid.c` lines 733-872): `newPTerm = rateError·kP`, `newDTerm = Δrate·(kD/dT)`, `newFFTerm = rateTarget·kFF`, `errorGyroIf += rateError·kI·dT`, summed and clamped to `pidSumLimit = ±500` (`getPidSumLimit()`, line 1505). Gain scaling (`pid.c` lines 582-589): `kP = P/31`, `kI = I/4`, `kD = D/1905`, `kFF = FF/31` (`FP_PID_RATE_P/I/D/FF_MULTIPLIER`, `flight/pid.h` lines 41-45). `firmware/main.py`'s `_scaled_pid()` applies this exact division; `pid.py`'s `PID` class gained a `kff` parameter (feedforward summed pre-clamp, excluded from the integrator, matching INAV).
    - **Config defaults are INAV's real `settings.yaml` numbers, not invented:** `pid_pitch_p=5, pid_pitch_i=7, pid_pitch_d=0, pid_pitch_ff=50` (`fw_p/i/d/ff_pitch`, lines 1925-1948); `pid_yaw_p=6, pid_yaw_i=10, pid_yaw_d=0, pid_yaw_ff=60` (`fw_p/i/d/ff_yaw`, lines 1973-1996) — pitch, roll, *and* yaw all default D to 0 upstream (`fw_d_roll=0` too, line 1966), confirming this isn't fixed-wing- or yaw-specific: INAV leans on feedforward instead of D across the board. Range 0-255 on all P/I/D/FF/level-P gains matches INAV's own `RPYL_PID_MIN`/`RPYL_PID_MAX` (`settings.yaml` lines 220-221).
    - Output normalization: our mixer expects [-1, 1], INAV's servo/mixer code (`servos.c` lines 143-144) maps `axisPID`'s native ±500 range linearly onto full servo throw — so `main.py` divides the PID+FF sum by 500 before handing it to `mixer.mix()`, rather than rescaling every gain to fit [-1, 1] directly. This keeps every gain and constant identical to INAV's real numbers.
    - Yaw's turn-coordination term (`turn_assist_gain`, see below) is folded into the same rate target the inner loop already consumes — added before computing `rateError`, and also passed as that loop's `feedforward_input`, so it benefits from the FF term too.
  - Throttle passthrough in this mode too (no altitude/speed hold).
- **No roll axis / actuator — grounded in INAV, with one justified deviation:** verified against INAV `master`, `pidController()` (`flight/pid.c`) always computes an independent roll-axis PID regardless of airframe; whether it reaches a servo is entirely the servo-mixer table's weighting (`servoMixer()`, `flight/servos.c`) — a no-aileron airframe's mixer simply has no rule routing `INPUT_STABILIZED_ROLL` anywhere, so the roll PID output is computed but goes nowhere. INAV *does* couple roll into yaw for exactly this kind of airframe via `pidTurnAssistant()` (`flight/pid.c`), gated behind a switchable "Turn Assistant" flight mode: it converts roll-stick-derived bank angle into an earth-frame turn rate via `GRAVITY_CMSS * tan(bankAngle) / airspeed`, added to the yaw rate target. **Deviation:** that formula needs airspeed, which this build doesn't have (no pitot; GPS is deferred with autonomous nav) — so `turn_assist_gain` is a linear roll-stick→yaw-rate scale instead of the physics-based tan/airspeed term. Also, per owner decision, coupling is always-on in stabilized mode rather than gated behind a dedicated switch channel (no channel budget for a 7th switch in the MVP).
  - Consequence for the parameter table: no `pid_roll_*` or `rate_roll_dps` — those axes/params don't exist.
- **Autonomous mode:** deferred with [Autonomous navigation design](./autonomous-navigation.md). For the MVP, the mode-switch position that would select it falls back to stabilized behavior — see [Flight modes, arming & failsafe](./flight-modes-arming-failsafe.md).
- **V-tail mixer:** linear mix, `left = left_pitch·pitch + left_yaw·yaw`, `right = right_pitch·pitch + right_yaw·yaw`, each clamped to [-1, 1] — as implemented in `firmware/mixer.py`. Gains are configurable (see parameter table below); no differential-throw or exponential curves for the MVP. Consumes the already-normalized (÷500) pitch/yaw commands from the cascade above.
- **Parameter table:** adopt `firmware/config.py`'s `SCHEMA` as canonical — PID+FF gains (pitch P/I/D/FF, yaw P/I/D/FF), level-P + rate-limit (pitch outer loop), pitch angle max, yaw rate scale, turn-assist gain, mixer gains (4x), servo endpoints (µs, 4x), CRSF channel map (6x, including `channel_roll` even though roll now feeds turn-assist rather than a roll axis), arm throttle threshold, failsafe link timeout, WiFi SSID/password. All web-configurable per owner's decision.
- Transpile-from-INAV strategy (pid.c/mixer.c/imu.c) stands per the assumptions above; the MVP simplifies INAV's structure to exactly the modes and axes listed here, but the gain pipeline itself (constants, defaults, ranges) is now a direct, verified transpile rather than an invented approximation.
